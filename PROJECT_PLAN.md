# Telegram Mini App для планирования выпускного

## 1. Цель продукта

Создать Telegram Mini App для группы студентов, где можно:

- смотреть идеи мест для выпускного на карте;
- предлагать новые места;
- голосовать или показывать интерес к местам;
- создавать временные сборы средств;
- добавлять товары/услуги в прайс-лист сбора;
- видеть общий бюджет и остаток;
- после дедлайна автоматически рассчитать сумму к оплате для участников;
- не отправлять счета тем, кто отказался участвовать;
- в будущем использовать приложение для других групп.

Приложение запускается внутри Telegram, поэтому интерфейс проектируется как мобильное приложение, а не как обычный сайт.

## 2. Роли пользователей

### Участник

- входит через Telegram;
- видит активные события и сборы своей группы;
- отмечает, участвует он или нет;
- предлагает товары в прайс-лист;
- предлагает места;
- голосует за места;
- видит свою итоговую сумму к оплате;
- отмечает оплату, если это разрешено правилами группы.

### Организатор

- создает выпускной/событие;
- добавляет участников;
- создает сбор средств;
- задает дедлайн и общий бюджет;
- модерирует товары и места;
- фиксирует финальный прайс-лист;
- запускает рассылку счетов;
- отмечает оплаты вручную, если нет платежной интеграции.

### Администратор системы

- управляет группами;
- видит технические ошибки;
- может заблокировать проблемные события или пользователей;
- настраивает интеграции.

## 3. Основные сущности

### Group

Группа или класс студентов. Нужна для масштабирования, чтобы другую группу можно было подключить без переписывания приложения.

Поля:

- название;
- Telegram chat id, если приложение связано с конкретным чатом;
- список участников;
- настройки валюты;
- настройки приватности.

### User

Пользователь Telegram.

Поля:

- Telegram user id;
- имя;
- username;
- аватар, если нужен;
- роль в группе;
- статус участия.

### Event

Выпускной или другое мероприятие.

Поля:

- название;
- описание;
- дата мероприятия;
- группа;
- статус: draft, active, archived;
- настройки доступа.

### Participation

Связь пользователя с мероприятием.

Статусы:

- участвует;
- не участвует;
- думает;
- не ответил.

Эта сущность важна для рассылки: счета получают только участники со статусом "участвует".

### PlaceIdea

Идея места для выпускного.

Поля:

- название;
- описание;
- адрес;
- координаты;
- ссылка на источник;
- цена аренды или ориентировочная цена;
- вместимость;
- фото;
- автор идеи;
- статус модерации;
- цвет/уровень интереса;
- количество голосов.

### Fundraising

Временный сбор средств.

Пример: "Сбор средств на продукты".

Поля:

- название;
- описание;
- событие;
- общий бюджет;
- дедлайн;
- статус: draft, active, locked, finished, cancelled;
- правила распределения оплаты;
- дата финального расчета.

### PriceItem

Товар или услуга внутри сбора.

Поля:

- название;
- категория;
- количество;
- единица измерения;
- цена за единицу;
- итоговая цена;
- автор предложения;
- статус: proposed, approved, rejected, purchased;
- комментарий;
- ссылка на магазин;
- приоритет: обязательное, желательно, опционально.

### Invoice

Счет участника после завершения сбора.

Поля:

- пользователь;
- сбор;
- сумма;
- статус: pending, paid, cancelled;
- дата отправки;
- дата оплаты;
- способ оплаты;
- комментарий организатора.

## 4. Правила прайс-листа

Бюджет сбора не должен уходить ниже 0. Рекомендуемая логика:

- у сбора есть `target_amount`;
- у каждого подтвержденного товара есть `total_price`;
- остаток считается как `target_amount - sum(approved_items.total_price)`;
- товар нельзя утвердить, если после утверждения остаток станет меньше 0;
- предложенные товары могут превышать бюджет, но они не влияют на остаток, пока не утверждены организатором.

Такой подход удобнее, чем сразу запрещать предложения: студенты могут предлагать идеи, а организатор решает, что реально войдет в финальный список.

Принятые решения:

- Участник не редактирует товар после добавления. Причина: он может резко заменить один товар на другой, а организатор узнает об этом поздно. Изменения можно оставить как идею для будущей версии, но в MVP товар после отправки фиксируется.
- Модерации каждого товара в MVP нет. Возможность модерации остается для будущей версии.
- Нужна проверка дублей. Если похожий товар уже есть, интерфейс показывает подсказку. Пример: пользователь пишет "кол", приложение предлагает уже добавленную "колу". Если пользователь выбирает существующий товар, он добавляется как дополнительное предложение/поддержка существующей позиции, а организатор получает уведомление.
- Категории товаров нужны.
- Голосование за товары в MVP не нужно, но можно оставить как идею для будущей версии.
- История изменений цены в MVP не нужна.
- Если после финализации остался бюджет, остаток показывается организатору отдельным полем. Счета участникам создаются только на фактически утвержденную сумму, то есть остаток не собирается.
- Итоговую сумму нужно делить по индивидуальным долям, потому что есть участники, которые пьют алкоголь, и участники, которые не пьют.
- Суммы должны быть целыми числами без десятых. Пример: `10000` правильно, `10000.50` неправильно.
- Факт оплаты подтверждает организатор.

Открытый вопрос:

- Как считать цену, если она примерная. Нужно отдельно решить, будет ли у товара тип цены: точная, примерная, диапазон или требует уточнения.

### Дубли товаров

Для дублей нужна не жесткая блокировка, а умная подсказка:

1. Пользователь вводит название товара.
2. Frontend отправляет поисковый запрос по существующим товарам сбора.
3. Backend возвращает похожие товары по названию и категории.
4. Пользователь может выбрать существующий товар вместо создания нового.
5. Если он выбирает существующий товар, система фиксирует, что еще один участник предложил/поддержал эту позицию.
6. Организатор получает уведомление, что к существующему товару добавилась новая поддержка или дополнительное количество.

Для MVP достаточно поиска по `icontains` и нормализации регистра. Позже можно добавить более умный fuzzy search.

### Индивидуальные доли

Участникам нужны доли или категории участия. Базовый вариант:

- обычная доля;
- без алкоголя;
- индивидуальная доля;
- освобожден от оплаты.

Для товаров можно добавить признак:

- общий товар;
- алкоголь;
- индивидуальная позиция;
- оплачивает только выбранная группа участников.

Тогда счет считается не одной общей формулой, а суммой частей:

```text
счет_участника = доля_общих_товаров + доля_алкоголя_если_участник_пьет + индивидуальные_позиции
```

## 5. Расчет счетов после дедлайна

После дедлайна сбор переводится в статус `locked`. Новые товары больше нельзя добавлять или редактировать.

Затем система:

1. Берет только утвержденные товары.
2. Считает итоговую сумму.
3. Берет только участников со статусом "участвует".
4. Делит сумму по выбранному правилу.
5. Создает счета.
6. Отправляет уведомления в Telegram.

Базовое правило распределения для MVP с индивидуальными долями:

```text
сумма_участника = доля_общих_товаров + доля_категорий_участника + индивидуальные_позиции
```

Суммы хранятся и показываются целыми числами в тенге, без десятых. Остаток от округления нужно фиксировать отдельно, чтобы итоговая сумма счетов совпадала с финальной суммой сбора.

Остаток бюджета после финализации не распределяется между участниками. Он отображается организатору как `remaining_budget`.

## 6. Участие и рассылка

Нужна отдельная панель участников:

- список всех студентов;
- статус участия;
- кому отправлять счета;
- кто уже оплатил;
- кто не оплатил;
- кто не ответил.

Рассылка счетов не должна идти всем подряд. Минимальное правило:

- `participation_status = participating` -> отправлять счет;
- `not_participating` -> не отправлять;
- `thinking` или `unknown` -> показать организатору предупреждение перед рассылкой.

Telegram-уведомления:

- приглашение подтвердить участие;
- напоминание о дедлайне сбора;
- уведомление о финальном счете;
- напоминание об оплате;
- уведомление организатору о новой идее или новом товаре.

## 7. Карты и места

В MVP используется Yandex Maps.

### Что должно быть на карте

- точки мест;
- разные цвета по уровню интереса;
- фильтры по цене, вместимости, статусу, району;
- карточка места по нажатию;
- ссылка "открыть маршрут" во внешнем приложении;
- возможность добавить место вручную по адресу или координатам.

Для дизайнера важно: у каждого места должна быть не только точка на карте, но и подробное описание. В карточке места нужно показать, что там есть: вместимость, ориентировочная цена, адрес, фото, условия аренды, наличие кухни/мангала/музыки/спальных мест/парковки, ограничения, плюсы, минусы и комментарий автора идеи.

### Цвет интереса

Пример шкалы:

- серый: мало данных или нет голосов;
- синий: новая идея;
- зеленый: высокий интерес;
- желтый: спорная идея;
- красный: дорого, мало голосов или есть проблема.

Лучше не делать цвет только по голосам. Более полезная формула:

```text
интерес = голоса + избранное - жалобы - штраф за высокую цену - штраф за малую вместимость
```

### Интеграция карт

Выбранный вариант: Yandex Maps API.

Причины:

- хорошо подходит для СНГ и Казахстана;
- есть поиск адресов;
- есть привычная карта и маршруты;
- подходит для отображения точек мест и карточек.

Нужно учитывать лимиты и условия использования API. Для разработки ключ хранится в переменных окружения, а не в коде.

## 8. Рекомендуемый стек

### Backend

Использовать Django, потому что в приложении есть:

- пользователи и роли;
- дедлайны;
- фоновые задачи;
- расчеты счетов;
- история действий;
- модерация;
- будущая мультигрупповая логика.

Рекомендуемый набор:

- Python;
- Django;
- Django REST Framework;
- PostgreSQL;
- Redis для кэша и фоновых задач, если хостинг позволяет;
- Celery или Django-Q для дедлайнов и рассылок;
- pytest или Django TestCase для тестов.

Если бесплатный хостинг не дает Redis, на MVP можно заменить фоновые задачи cron-задачей, которая раз в несколько минут проверяет просроченные сборы.

### Frontend

Рекомендуемый вариант:

- React;
- Vite;
- TypeScript;
- Telegram Web Apps SDK;
- React Router;
- TanStack Query для API-запросов и кэширования;
- Zustand или Redux Toolkit, если локального состояния станет много.

Это даст поведение "как React": переходы между страницами без полной перезагрузки.

### Hosting

Vercel хорошо подходит для фронтенда, но не является лучшим местом для обычного Django-сервера.

Практичный вариант:

- Frontend: Vercel;
- Backend: Render, Railway, Fly.io, PythonAnywhere или другой Python-хостинг;
- Database: Supabase Postgres, Neon Postgres или база от backend-хостинга;
- Redis: Upstash Redis или Redis от backend-хостинга, если нужен.

## 9. Telegram Mini App

Нужно использовать Telegram Web Apps.

Критичные требования:

- авторизация через `initData`;
- проверка подписи `initData` на backend;
- нельзя доверять Telegram user id, пришедшему только с frontend;
- тема приложения должна читать `themeParams` из Telegram;
- приложение должно корректно работать в темной, светлой и системной теме;
- все важные действия подтверждать на backend.

Бот нужен для:

- запуска Mini App;
- отправки уведомлений;
- отправки счетов;
- напоминаний;
- приглашений участникам.

## 10. Оптимизация и масштабирование

Сразу проектировать как multi-tenant:

- все события привязаны к Group;
- все пользователи имеют роль внутри конкретной Group;
- запросы всегда фильтруются по group id;
- нельзя получить данные чужой группы.

Кэширование:

- кэшировать список мест;
- кэшировать агрегаты голосов;
- кэшировать summary по сбору: бюджет, потрачено, остаток;
- не кэшировать персональные счета без аккуратной привязки к пользователю;
- сбрасывать кэш после добавления товара, голоса или изменения бюджета.

Индексы PostgreSQL:

- `group_id`;
- `event_id`;
- `fundraising_id`;
- `telegram_user_id`;
- `deadline`;
- `status`.

Асинхронные задачи:

- обработка дедлайнов;
- создание счетов;
- Telegram-рассылки;
- напоминания;
- пересчет агрегатов, если он станет тяжелым.

## 11. API MVP

Примерные endpoints:

- `POST /api/auth/telegram/` - вход через Telegram Mini App;
- `GET /api/me/` - текущий пользователь;
- `GET /api/events/` - события группы;
- `GET /api/events/{id}/` - детали события;
- `PATCH /api/events/{id}/participation/` - изменить участие;
- `GET /api/events/{id}/places/` - места;
- `POST /api/events/{id}/places/` - предложить место;
- `POST /api/places/{id}/vote/` - голос за место;
- `GET /api/events/{id}/fundraisings/` - сборы;
- `POST /api/events/{id}/fundraisings/` - создать сбор;
- `GET /api/fundraisings/{id}/items/` - товары;
- `POST /api/fundraisings/{id}/items/` - предложить товар;
- `PATCH /api/items/{id}/approve/` - утвердить товар;
- `PATCH /api/items/{id}/reject/` - отклонить товар;
- `POST /api/fundraisings/{id}/finalize/` - завершить сбор и создать счета;
- `GET /api/invoices/my/` - мои счета;
- `PATCH /api/invoices/{id}/paid/` - отметить оплату.

## 12. Дизайн-ТЗ для дизайнера

### Формат

Дизайн нужен для Telegram Mini App, mobile-first.

Основные размеры:

- основной макет: 360px, 390px, 430px шириной;
- желательно проверить 320px для маленьких экранов;
- отдельный desktop-макет не является приоритетом, но приложение не должно ломаться на широкой web-версии Telegram.

### Темы

Нужно подготовить:

- light theme;
- dark theme;
- system theme.

Системная тема должна использовать параметры Telegram, если они доступны:

- background;
- text color;
- hint color;
- button color;
- secondary background.

### Навигация

Рекомендуемые основные вкладки:

- Главная;
- Места;
- Сборы;
- Участники;
- Профиль.

Для организатора добавить отдельные действия:

- создать сбор;
- добавить место;
- финализировать сбор;
- отправить счета;
- управлять участниками.

### Основные экраны

Нужны макеты:

- onboarding/первый вход;
- выбор или просмотр события;
- главная события;
- карта мест;
- карточка места;
- добавление места;
- список сборов;
- детали сбора;
- добавление товара;
- модерация товаров;
- финальный расчет;
- мой счет;
- список участников;
- настройки темы;
- empty states;
- loading states;
- error states.

### UI-требования

- интерфейс должен быть удобен одной рукой;
- основные действия должны быть в нижней части экрана;
- формы короткие, с понятной валидацией;
- числа и суммы должны быть хорошо видны;
- нельзя перегружать экран декоративными элементами;
- карточки должны быть компактными;
- для статусов использовать цвет и текст одновременно;
- кнопки опасных действий должны требовать подтверждения;
- экран карты должен оставлять место для bottom sheet с деталями места.
