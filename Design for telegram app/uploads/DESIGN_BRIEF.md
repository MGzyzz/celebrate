# ТЗ для дизайнера: Telegram Mini App для выпускного

## 1. Контекст

Нужно спроектировать мобильный интерфейс Telegram Mini App для планирования выпускного.

Приложение открывается внутри Telegram, поэтому дизайн должен ощущаться как компактное мобильное приложение, а не как сайт. Основные сценарии: выбрать место, предложить место, подтвердить участие, добавить товары в сбор, посмотреть счет, организатору управлять участниками и оплатами.

## 2. Целевая аудитория

- студенты, которые участвуют в выпускном;
- организаторы выпускного;
- пользователи, которые могут редко заходить в приложение и должны быстро понять состояние события.

Интерфейс должен быть простым, быстрым и удобным одной рукой.

## 3. Платформа

Формат: Telegram Mini App.

Основные размеры макетов:

- 360px ширина;
- 390px ширина;
- 430px ширина;
- отдельно проверить 320px для маленьких экранов.

Широкий desktop-макет не является главным, но интерфейс не должен ломаться в web-версии Telegram.

## 4. Темы

Нужно подготовить три варианта:

- светлая тема;
- темная тема;
- системная тема.

Системная тема должна быть совместима с Telegram theme params:

- background;
- secondary background;
- text color;
- hint color;
- link color;
- button color;
- button text color.

Важно: цвета статусов должны быть различимы и в светлой, и в темной теме.

## 5. Навигация

Рекомендуемая нижняя навигация:

- Главная;
- Места;
- Сборы;
- Участники;
- Профиль.

Для обычного участника вкладка "Участники" может быть упрощенной или скрывать чувствительные данные. Для организатора она должна быть полноценной панелью управления.

## 6. Основные экраны

Нужно подготовить макеты:

- первый вход / onboarding;
- главная события;
- подтверждение участия;
- карта мест;
- список мест;
- карточка места;
- добавление места;
- список сборов;
- детали сбора;
- добавление товара;
- подсказка дубля товара;
- финальный счет участника;
- список участников;
- панель организатора;
- финализация сбора;
- подтверждение отправки счетов;
- профиль и настройки темы;
- empty state;
- loading state;
- error state.

## 7. Главная события

На главной нужно показать:

- название выпускного;
- дату, если она известна;
- статус участия пользователя;
- активный сбор;
- краткий бюджет: собрано/план/остаток;
- топ мест или выбранное место;
- ближайший дедлайн;
- быстрые действия.

Быстрые действия:

- подтвердить участие;
- открыть сбор;
- открыть карту;
- предложить место.

## 8. Участие

У пользователя должны быть статусы:

- участвую;
- не участвую;
- думаю;
- не ответил.

Важно показать пользователю, что счета отправляются только тем, кто участвует.

Для организатора нужен список участников:

- имя;
- статус участия;
- категория оплаты;
- статус оплаты;
- сумма счета;
- быстрый фильтр по статусам.

Категории оплаты:

- обычная доля;
- без алкоголя;
- индивидуальная доля;
- освобожден от оплаты.

## 9. Карта мест

Интеграция: Yandex Maps.

На карте должны быть:

- точки мест;
- разные цвета маркеров по уровню интереса;
- bottom sheet с краткой информацией по выбранному месту;
- фильтры;
- кнопка добавления места;
- кнопка открытия маршрута во внешнем приложении.

Цвета интереса:

- серый: мало данных;
- синий: новая идея;
- зеленый: высокий интерес;
- желтый: спорная идея;
- красный: проблема, высокая цена или низкий интерес.

## 10. Карточка места

У каждого места должна быть подробная карточка.

Показать:

- название;
- фото или галерею;
- адрес;
- расстояние или район, если доступно;
- ориентировочную цену;
- вместимость;
- описание;
- что там есть;
- условия аренды;
- плюсы;
- минусы;
- комментарий автора;
- количество голосов/интерес;
- кнопка "Открыть маршрут";
- кнопка "Поддержать идею";
- кнопка "Предложить другое место".

Блок "Что там есть" должен быть визуально понятным. Подходят компактные теги или строки с иконками:

- кухня;
- мангал;
- музыка;
- спальные места;
- парковка;
- посуда;
- бассейн;
- зона отдыха;
- ограничение по шуму;
- залог.

## 11. Сборы и прайс-лист

Сбор имеет:

- название;
- дедлайн;
- общий бюджет;
- утвержденную сумму;
- остаток бюджета;
- список товаров;
- статус.

Статусы сбора:

- черновик;
- активен;
- закрыт для изменений;
- завершен;
- отменен.

В деталях сбора нужно показать:

- прогресс бюджета;
- сколько дней осталось;
- утвержденные товары;
- предложенные товары;
- категории;
- кнопку добавления товара;
- предупреждение, если дедлайн близко.

## 12. Добавление товара

Форма добавления товара:

- название;
- категория;
- количество;
- единица измерения;
- цена;
- тип товара;
- комментарий;
- ссылка на магазин, необязательно.

Тип товара:

- общий;
- алкоголь;
- индивидуальный;
- только для выбранной группы участников.

После отправки обычный участник не редактирует товар. Нужно заранее показать понятный текст, что после добавления изменение будет недоступно.

## 13. Дубли товаров

Если пользователь вводит похожий товар, нужно показать подсказку.

Пример:

- пользователь пишет "кол";
- приложение показывает "Кола уже есть в списке";
- пользователь может выбрать существующую позицию;
- после выбора система добавляет поддержку или дополнительное количество к существующему товару.

Состояние подсказки должно быть заметным, но не мешать вводу.

## 14. Финальный счет

Суммы показываются только целыми числами без десятых.

Пример правильного отображения:

```text
10 000 тг
```

Пример неправильного отображения:

```text
10 000,50 тг
```

В счете участника показать:

- итоговую сумму;
- из чего она состоит;
- общая часть;
- алкогольная часть, если применимо;
- индивидуальные позиции;
- дедлайн оплаты;
- инструкцию для оплаты;
- статус оплаты.

Факт оплаты подтверждает организатор.

## 15. Панель организатора

Организатору нужны экраны:

- список участников;
- фильтры: участвует, не участвует, думает, не ответил, оплатил, не оплатил;
- детали участника;
- изменение категории оплаты;
- финальный расчет;
- остаток бюджета;
- отправка счетов;
- подтверждение оплаты.

Перед отправкой счетов нужно показать предупреждение:

- сколько человек получат счет;
- сколько человек не получат счет;
- сколько человек не ответили;
- итоговая сумма;
- остаток бюджета.

## 16. UI-требования

- Mobile-first.
- Основные действия должны быть доступны большим пальцем.
- Не перегружать экраны декоративными элементами.
- Карточки компактные.
- Числа и суммы должны хорошо читаться.
- Статусы показывать цветом и текстом одновременно.
- Опасные действия требуют подтверждения.
- Формы должны быть короткими и понятными.
- Ошибки в формах показывать рядом с полем.
- Пустые состояния должны объяснять, что делать дальше.
- Bottom sheet на карте не должен перекрывать всю карту без необходимости.

## 17. Компоненты

Нужны компоненты:

- place card;
- map bottom sheet;
- item row;
- category chip;

- кликабельный прототип основных сценариев;
- список иконок;
- правила отступов;
- правила цветов статусов;
- примеры длинных текстов и маленьких экранов.
